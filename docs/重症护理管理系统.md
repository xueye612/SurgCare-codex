# 重症护理管理系统

## 0. 全局约定（适用于全部模块）

### 0.1 统一概念

- 组织：集团/医院/院区/科室/病区（ICU）/护理单元
- 主体对象：用户、角色、权限、患者、床位、设备、医嘱、护理记录、告警、事件、指标
- 租户模型：支持单院单租户 / 多院多租户（建议一开始按“多院区”抽象，后续可升级为多租户）
- 数据权限：按组织层级、科室/病区、床位、患者分配
- 审计对象：登录、查询、修改、导出、静音、审批、接口调用

### 0.2 通用能力要求

- 全模块支持：分页、搜索、排序、导出（受权限控制）、字段级脱敏（受权限控制）
- 所有写操作：必须产生操作日志与审计事件
- 关键数据：具备历史版本/变更记录（至少核心表）
- 接口风格：REST/JSON（如需院内集成可补 HL7/FHIR 通道）

# 一、基础平台能力模块（所有系统都必须具备）

下面每个子模块都给到：功能介绍 + 功能清单 + 关键数据对象 + 关键接口建议 + 权限/审计要点。

## 1. 用户管理

### 1.1 目标

统一管理系统登录主体（医护/管理/信息科/第三方），支持多院区、多科室、岗位与职级，满足最小权限与可审计。

### 1.2 功能清单

- 用户新增/编辑/禁用/启用/删除（逻辑删除）
- 账号类型：院内职工、外协人员、第三方（厂商/科研）
- 账号认证：用户名+密码、短信/OTP（可选）、单点登录 SSO（可选）
- 密码策略：强度校验、过期策略、错误次数锁定、首次登录改密
- 用户归属：医院/院区/科室/病区/岗位/职称
- 用户分组：按岗位组/项目组/应急小组（用于通知与权限）
- 批量导入：Excel/接口导入（含校验与回滚）
- 离职/调岗：组织归属变更、权限自动回收
- 登录设备管理（可选）：绑定设备、限制登录端

### 1.3 关键数据对象

- `user`：id、username、name、mobile、email、status、org_path、dept_id、ward_id、title、position、password_hash、last_login_at…
- `user_role`：user_id、role_id
- `user_group`（可选）：用于通知组/应急小组

### 1.4 关键接口建议

- `POST /api/users` 新增
- `PUT /api/users/{id}` 编辑
- `GET /api/users` 列表（支持 org/科室/角色过滤）
- `POST /api/users/import` 批量导入
- `POST /api/users/{id}/disable` 禁用/启用
- `GET /api/users/{id}` 详情（含角色与数据权限摘要）

### 1.5 权限与审计要点

- “创建/编辑用户”属于高危权限：必须审计、可配置二次确认
- 用户敏感字段（手机号、身份证等）脱敏展示
- 用户删除只允许逻辑删除并审计原因

## 2. 角色与权限管理

### 2.1 目标

实现 RBAC（角色权限）+ 数据权限（组织/科室/床位/患者范围）+ 操作权限（读/写/删/导出/审批）三层控制。

### 2.2 功能清单

- 角色管理：创建、复制、启用/停用、绑定默认数据范围
- 权限点管理：菜单权限、页面权限、按钮权限、接口权限
- 数据权限：按组织层级（全院/院区/科室/病区/床位）、按患者归属（负责护士/管床医生）
- 权限模板：护理主任模板、护士模板、医生模板、信息科模板
- 权限校验：接口级强校验（后端为准）
- 授权审计：谁在何时给谁授权了什么权限
- 超级管理员：可配置数量、可审计其所有操作

### 2.3 关键数据对象

- `role`：id、name、status、data_scope_type、data_scope_value
- `permission`：id、code、name、type（menu/button/api）
- `role_permission`：role_id、permission_id
- `data_scope_rule`（可选）：更复杂的数据范围表达

### 2.4 关键接口建议

- `GET /api/roles`
- `POST /api/roles`
- `PUT /api/roles/{id}`
- `POST /api/roles/{id}/permissions` 绑定权限点
- `POST /api/roles/{id}/data-scope` 配置数据范围
- `GET /api/permissions/tree` 权限树

### 2.5 权限与审计要点

- 任何角色权限变化：必须记录审计事件（前后对比）
- 导出权限单独控制（防止数据外流）

## 3. 组织架构管理

### 3.1 目标

支撑“多院区/多科室/病区/床位”的组织层级，统一用于数据权限、统计口径、看板维度。

### 3.2 功能清单

- 组织树维护：医院/院区/科室/病区（ICU）/护理单元
- 人员归属：用户挂载组织节点
- 床位归属：床位挂载病区/护理单元
- 组织变更：迁移与历史追溯（避免统计口径断裂）
- 排班关联：排班基于病区/护理单元

### 3.3 关键数据对象

- `org_unit`：id、parent_id、type、name、code、status、sort、path
- `org_user`：org_unit_id、user_id

### 3.4 关键接口建议

- `GET /api/org/tree`
- `POST /api/org`
- `PUT /api/org/{id}`
- `POST /api/org/{id}/move` 迁移节点
- `GET /api/org/{id}/users`

### 3.5 权限与审计要点

- 组织变更属于高危：必须审计；关键统计要支持“按当时组织口径回看”

## 4. 自定义字段与表单引擎

### 4.1 目标

让医院能在不改代码的情况下扩展：护理评估表、记录单、交接清单、事件上报表等（强烈建议做成“配置驱动”）。

### 4.2 功能清单（核心）

- 字段类型：文本/数字/日期/时间/枚举/多选/人员/组织/文件/评分/公式计算
- 表单设计器：拖拽布局、分组、必填、校验规则、默认值
- 条件逻辑：字段显隐、联动选项、分支路径（如 SOFA 条件项）
- 表单版本：发布版本、草稿版本、历史版本回看
- 表单权限：哪些角色能看/填/改/导出
- 数据映射：表单字段映射到结构化表（或统一 EAV 存储）
- 审批流（可选）：某些表单提交后进入审核（如不良事件）

### 4.3 关键数据对象（建议）

- `form`：id、code、name、biz_type、version、status
- `form_field`：id、form_id、key、label、type、rules_json、options_json、sort
- `form_layout`：布局结构 JSON
- `form_record`：record_id、form_id、biz_id（如 patient_id）、data_json、version、created_by…

存储建议：

- 护理记录等高频数据，建议“结构化表 + 关键字段落表”，同时保留 `data_json` 作为扩展。
- 低频扩展字段可走 EAV 或 `data_json`。

### 4.4 关键接口建议

- `GET /api/forms?biz_type=...`
- `GET /api/forms/{code}/schema`
- `POST /api/forms/{code}/records` 提交
- `GET /api/forms/{code}/records?biz_id=...`
- `PUT /api/forms/{code}/records/{id}`（受权限与版本控制）
- `POST /api/forms/{code}/publish` 发布新版本

### 4.5 权限与审计要点

- 表单设计变更必须审计
- 表单记录修改必须留痕（字段级对比）

## 5. 数据字典管理

### 5.1 目标

统一管理可枚举主数据：告警级别、管路类型、护理动作类型、科室类型、设备品牌型号、药物分类映射等。

### 5.2 功能清单

- 字典分类：dict_type（如 alarm_level）
- 字典项：dict_item（code、name、sort、status）
- 多院区差异化：允许院区级覆盖（可选）
- 历史兼容：禁用不删，避免历史数据断裂
- 导入导出

### 5.3 关键接口建议

- `GET /api/dicts/{type}`
- `POST /api/dicts/{type}/items`
- `PUT /api/dicts/{type}/items/{id}`
- `POST /api/dicts/import`

### 5.4 权限与审计要点

- 字典变更影响全局：必须审计，建议只给信息科/管理员

## 6. 操作日志管理

### 6.1 目标

记录“谁在什么时间，对什么对象做了什么操作，改了哪些字段”，用于追责、复盘与合规。

### 6.2 功能清单

- 记录范围：新增/修改/删除/导出/打印/审批/静音/确认告警
- 字段级差异：before/after（重要表必须）
- 关联对象：患者、床位、医嘱、护理记录、设备、告警
- 查询与筛选：按用户、模块、对象、时间
- 导出（受权限控制）
- 日志保留策略：冷热归档

### 6.3 关键数据对象

- `op_log`：id、module、action、object_type、object_id、operator_id、ip、ua、before_json、after_json、created_at

### 6.4 关键接口建议

- `GET /api/logs/ops`（分页查询）
- `GET /api/logs/ops/{id}`（详情/字段差异）

## 7. 登录日志管理

### 7.1 目标

记录登录成功/失败、异常登录、账号锁定、强制登出等安全事件。

### 7.2 功能清单

- 登录成功记录：时间、IP、地点（可选）、终端类型
- 登录失败记录：原因（密码错误/账号禁用/锁定）
- 异常检测：短时间多次失败、异地登录、非常用设备
- 安全动作：强制登出、锁定、解锁、重置密码
- 安全报表：高风险账号列表

### 7.3 关键接口建议

- `GET /api/logs/login`
- `POST /api/security/users/{id}/lock`
- `POST /api/security/users/{id}/force-logout`

## 8. 审计与追踪系统

### 8.1 目标

不仅是日志，还要“可形成审计报表 + 不可篡改 + 可追溯链路”。

### 8.2 功能清单

- 审计事件：越权访问、敏感数据查看、批量导出、权限变更、告警静音
- 审计链路：从接口请求 → 业务对象 → 数据变更 → 责任人
- 不可篡改：审计日志追加写（可选 hash 链）
- 审计报表：按月输出关键行为统计
- 合规策略：保留期、脱敏策略、审计员角色

### 8.3 关键接口建议

- `GET /api/audit/events`
- `GET /api/audit/reports?month=YYYY-MM`

## 9. 消息通知系统

### 9.1 目标

将“告警、任务、医嘱执行超时、质控缺陷”等事件分发到 PC/移动端/大屏，形成闭环。

### 9.2 功能清单

- 通知渠道：站内信、短信（可选）、企业微信/钉钉（可选）、推送（可选）
- 订阅规则：按角色/病区/床位/患者责任人订阅
- 通知模板：可配置变量（患者名、床号、告警级别）
- 通知状态：已读/未读/确认/完成
- 任务化：通知可一键转为任务（如“去床旁确认告警”）

### 9.3 关键接口建议

- `GET /api/notifications`
- `POST /api/notifications/{id}/read`
- `POST /api/notify/rules` 配置订阅规则

## 10. 系统配置中心

### 10.1 目标

把可变策略放配置里：告警阈值模板、评分算法参数、权限策略、日志保留期、字典覆盖等。

### 10.2 功能清单

- 配置分类：安全、告警、表单、接口、存储、展示
- 多层级配置：全院默认 + 院区覆盖 + 病区覆盖
- 配置版本：发布、回滚
- 灰度开关：新功能开关（Feature Flag）
- 参数校验：配置变更必须校验

### 10.3 关键接口建议

- `GET /api/configs?scope=...`
- `PUT /api/configs/{key}`
- `POST /api/configs/{key}/publish`
- `POST /api/configs/{key}/rollback`

## 11. 多院区/多科室支持

### 11.1 目标

一套系统服务多个院区/科室，做到数据隔离、配置隔离、权限隔离、统计可汇总。

### 11.2 功能清单

- 院区维度：院区独立组织树、床位、设备
- 院区配置覆盖：告警阈值、表单模板
- 跨院区权限：集团管理员可汇总查看
- 跨院区统计：床位使用率、感染率等汇总
- 数据隔离策略：同表加院区字段/租户字段

## 12. 接口与 API 管理

### 12.1 目标

支持与 HIS/LIS/PACS/EMR/PIVAS/设备网关对接，同时也为移动端/大屏提供稳定 API。

### 12.2 功能清单

- API 网关（可选）：鉴权、限流、日志、版本
- 接口标准：REST + 可扩展 HL7/FHIR
- 幂等机制：防止重复提交（医嘱执行、事件上报）
- 消息队列（可选）：设备数据/告警高频流

### 12.3 关键接口建议

- `GET /api/health` 健康检查
- `GET /api/metrics` 指标（给监控系统）

### 13.2 功能清单

- 统一登录：同一账号多端在线策略

## 二、患者与床位管理模块

### 2.1 目标
建立 ICU “床位—患者—在床周期（ICU Stay）”的主数据体系，支持床位状态实时可视、隔离资源管理、应急空床预留，形成可统计的床位使用率与住院天数口径，为后续所有业务（采集/护理/医嘱/告警/质控）提供统一主键与权限范围。

### 2.2 功能清单

#### 2.2.1 ICU床位管理
- 床位档案维护：床号、床位类型（普通/抢救/隔离）、归属病区/护理单元
- 床位状态维护：空床/在用/清洁中/维修中/封床（不可用）
- 床位标签：隔离条件、设备能力（如是否可接监护、呼吸机位等，可选）
- 床位变更历史：床位类型/归属/状态变更留痕与追溯

#### 2.2.2 床位状态监控
- 病区床位一览：床位状态、当前患者摘要、责任护士/医生
- 状态联动：
  - 入科/转入：床位自动变为“在用”
  - 转床：原床位→清洁中（或空床），新床位→在用
  - 出科/出院：床位→清洁中→空床（流程可配置）
- 异常状态检测：同一床位同时存在两个“在床周期”；或患者存在两个“在床周期”（冲突校验）

#### 2.2.3 患者基本信息
- 患者主档：基础信息（姓名、性别、出生日期、病案号/住院号/HIS患者ID等）
- ICU在床信息：入科时间、床位、诊断摘要、隔离标记、责任护士/医生
- 与HIS对接（可选）：患者主档拉取/同步（增量更新、冲突策略）

#### 2.2.4 住院天数统计（口径明确）
- ICU住院天数：以 ICU Stay 计算（当前时间-入科时间，按天/小时口径可配置）
- 支持“统计时点回看”：按某日0点/某时刻计算住院天数
- 支持“转入/转出/转床”不影响住院天数连续性（只变化 bed_id）

#### 2.2.5 床位使用率统计
- 使用率口径：
  - 分母：可用床位数（排除维修/封床/长期预留可配置）
  - 分子：在用床位数（按时点或按天统计）
- 统计维度：院区/病区/护理单元/床位类型
- 输出：日/周/月趋势，峰值、平均值
- 阈值预警（可选）：例如>85%提示扩容/调配风险（阈值配置中心维护）

#### 2.2.6 隔离床位管理
- 隔离床位标识：具备隔离条件的床位清单
- 隔离状态：
  - 床位为“隔离使用中”（患者隔离）
  - 隔离结束后“终末消毒/清洁中”时长记录
- 隔离资源统计：隔离床位占用率、周转时间、等待队列（可选）

#### 2.2.7 应急空床预留机制
- 预留操作：将床位标记为“应急预留”，可设置原因/截止时间
- 使用规则（可配置）：
  - 预留床位是否允许被普通入科占用（默认不允许）
  - 占用预留床位是否需要审批（建议需要）
- 预留审批（可选）：护士长/护理主任审批占用申请
- 预留到期：自动提醒或自动释放（策略可配置）
- 全流程审计：谁预留、谁申请占用、谁审批、何时释放

### 2.3 关键数据对象
- `bed`：床位档案（床号、类型、归属、状态、隔离能力、预留状态）
- `patient`：患者主档（院内唯一患者标识，可对接HIS）
- `icu_stay`：在床周期（入科/转床/出科/责任人、隔离标记）
- `bed_status_history`：床位状态变更历史（可选但强烈建议）
- `reservation`：应急预留/占用申请/审批记录（可选，建议做）

### 2.4 关键接口建议
- 床位
  - `GET /api/beds?ward_id=&status=&type=` 床位列表（用于床位一览）
  - `POST /api/beds` 新增床位
  - `PUT /api/beds/{id}` 编辑床位档案
  - `POST /api/beds/{id}/status` 设置床位状态（封床/维修/清洁中等）
  - `GET /api/beds/{id}/history` 床位变更历史
- 患者与在床周期
  - `GET /api/patients?keyword=` 患者检索
  - `POST /api/patients` 新建患者（无HIS时）
  - `GET /api/icu-stays?ward_id=&status=` 在床患者列表
  - `POST /api/icu-stays/admit` 入科/收治（创建 ICU Stay）
  - `POST /api/icu-stays/{id}/transfer-bed` 转床
  - `POST /api/icu-stays/{id}/discharge` 出科/出院
- 统计
  - `GET /api/stats/bed-occupancy?ward_id=&from=&to=&granularity=day` 床位使用率
  - `GET /api/stats/los?ward_id=&from=&to=` 住院天数（LOS）统计
- 隔离/预留
  - `POST /api/beds/{id}/isolation/enable` 标记床位具备隔离能力（可选）
  - `POST /api/beds/{id}/reserve-emergency` 应急预留
  - `POST /api/beds/{id}/reserve-release` 释放预留
  - `POST /api/beds/{id}/reserve-occupy-apply` 申请占用预留床位（可选）
  - `POST /api/beds/{id}/reserve-occupy-approve` 审批占用申请（可选）

### 2.5 权限与审计要点
- **床位状态/预留/转床/出科**属于高风险操作：
  - 必须记录操作日志（前后对比）
  - 必须记录审计事件（event_type：bed_status_change / emergency_reserve / bed_transfer）
- **数据权限**：床位与在床患者的查看/编辑受“病区/护理单元范围”控制
- **冲突校验**：任何“入科/转床”必须做并发控制（避免双占床、双在床周期）

## 三、临床数据采集模块

### 3.1 目标
实现 ICU 多设备、多厂商数据统一接入与治理：生命体征、波形、呼吸机、输液泵、出入量等数据自动采集，并通过时钟同步与完整性校验，保证“可用、可信、可回放”，为告警、评分、AI与质控提供数据底座。

### 3.2 功能清单

#### 3.2.1 生命体征自动采集
- 支持从床旁监护设备自动采集 HR/BP/RR/SpO₂/Temp 等
- 自动入库并关联 ICU Stay（按床位/患者映射）
- 允许人工补录/修正（需留痕）

#### 3.2.2 高频波形采集与存储
- 采集 ECG/ABP/SpO₂ 波形（按医院实际选配）
- 波形存储策略：
  - 热数据：可快速回放（近24h/72h）
  - 冷数据：归档压缩（近30天/半年，可配置）
- 波形回放与截图导出（导出权限严格控制）

#### 3.2.3 呼吸机数据采集
- 采集基础参数：模式、FiO₂、PEEP、潮气量、分钟通气等（按厂商能力）
- 采集呼吸机报警（可选与告警模块打通）
- 参数趋势回放

#### 3.2.4 输液泵数据采集
- 采集泵运行状态、速率、剂量（需药物库/映射时在医嘱模块联动）
- 采集泵报警（可选与告警模块打通）
- 支持“泵参数执行留证”（与医嘱执行闭环相关）

#### 3.2.5 出入量自动统计
- 输液入量：来自泵/医嘱执行/人工录入（多来源合并）
- 出量：尿量（设备/称重/人工录入）、引流量、呕吐等
- 自动计算24h液体平衡（并输出趋势）

#### 3.2.6 数据时钟同步机制
- 统一时间基准：服务端NTP校时 + 网关校时
- 设备时钟偏差监测：偏差超过阈值报警（给信息科/运维）
- 采集记录保留“设备时间”与“入库时间”（便于追溯）

#### 3.2.7 数据完整性校验机制
- 校验项：
  - 缺失：关键指标缺失率
  - 异常值：单位/范围不合理（如SpO₂>100）
  - 丢包：波形丢包率、延迟
  - 映射：床位/患者映射是否正确
- 自动生成采集质量报表（接入率、延迟、丢包）

### 3.3 关键数据对象
- `device`：设备档案（类型、厂商、型号、序列号、归属床位/病区）
- `device_binding`：床位/设备绑定关系（可选，强烈建议）
- `vital_sign`：生命体征时间序列（汇总值）
- `waveform`：波形索引（实际数据可能在对象存储/TSDB）
- `vent_data`：呼吸机参数时间序列
- `pump_data`：输液泵参数时间序列
- `io_record`：出入量记录
- `ingest_health`：采集健康度（接入率/延迟/丢包/时钟偏差）

### 3.4 关键接口建议
> 采集接口通常由“网关/中间件”调用，需单独鉴权（API Client / 白名单 / mTLS）

- 设备接入与绑定
  - `POST /api/integration/devices/register` 设备注册
  - `POST /api/integration/devices/bind` 设备绑定床位
  - `POST /api/integration/devices/unbind` 解绑
- 数据上报（高频建议走MQ或批量上报）
  - `POST /api/integration/vitals/ingest` 生命体征上报（可批量）
  - `POST /api/integration/waveforms/ingest` 波形上报/索引上报
  - `POST /api/integration/vent/ingest` 呼吸机数据上报
  - `POST /api/integration/pump/ingest` 泵数据上报
  - `POST /api/integration/io/ingest` 出入量上报
- 临床查询（给前端）
  - `GET /api/icu-stays/{id}/vitals?from=&to=&granularity=` 体征趋势
  - `GET /api/icu-stays/{id}/waveforms?type=&from=&to=` 波形索引/回放地址
  - `GET /api/icu-stays/{id}/vent?from=&to=` 呼吸机趋势
  - `GET /api/icu-stays/{id}/pump?from=&to=` 泵趋势
  - `GET /api/icu-stays/{id}/io?from=&to=` 出入量与平衡
- 采集质量与同步
  - `GET /api/ingest/health?ward_id=&from=&to=` 采集健康度报表
  - `GET /api/ingest/time-sync/status` 时钟同步状态（运维）

### 3.5 权限与审计要点
- 临床查看：受“病区/床位/患者范围”控制
- 波形导出/截图：单独权限点（防外泄），产生审计事件 `sensitive_export`
- 人工修正数据：必须留痕（before/after），产生审计事件 `data_override`
- 采集接口：必须区分“系统用户/设备客户端”，接口调用必须可追踪（client_id、trace_id）

## 四、护理工作台模块（护士核心工作系统）

### 4.1 目标
将 ICU 护士高频工作“任务化+清单化+自动采集+缺失阻断”，做到：  
- 做了就留证（减少后补）  
- 漏项可预警（减少风险）  
- 交接可一键生成（提高效率）  
并为质控指标提供可计算数据。

### 4.2 功能清单

#### 4.2.1 电子床旁交接
- 交接清单模板（可配置）：气道/血流动力学/镇静镇痛/管路/输注/隔离/风险点
- 关键项必填与缺失阻断（可配置）
- 交接双方签名/确认（电子签名/账号确认）
- 一键生成交接摘要（用于交接记录与后续质控）

#### 4.2.2 巡视任务管理
- 护理任务模板（可配置）：每小时体征、每2小时翻身、吸痰、口腔护理等
- 时间窗提醒：提前提醒、到期提醒、逾期提醒
- 任务闭环：完成时间、执行人、执行记录
- 护士工作量统计（任务数、准时率）

#### 4.2.3 护理记录系统
- 结构化护理记录（可配置表单）+ 自由文本
- 自动抓取：生命体征/出入量/部分设备参数（减少手填）
- 记录修改留痕：字段级对比、原因（可选）
- 支持“当班完成率”统计

#### 4.2.4 评分系统（APACHE/SOFA/GCS）
- 自动计算：从既有数据中取数（时间窗规则可配置）
- 手动补录：缺失项提示并允许补录
- 评分趋势：按日/按班次展示
- 与告警/风险提示联动（可选）

#### 4.2.5 管路管理（CVC/PICC/导尿/气道）
- 管路建档：类型、置管时间、部位、状态
- 每日留置必要性评估提醒（与院感联动）
- 维护记录：敷料更换、冲管、固定检查（可配置）
- 风险事件：渗血、脱落、堵管记录与上报

#### 4.2.6 翻身与压疮管理
- 翻身计划：2小时一次（可按患者配置）
- 翻身执行记录：时间、体位、执行人
- 压疮风险评估（Braden等，可配置）
- 压疮事件记录：分期、部位、照片（照片权限控制）

#### 4.2.7 呼吸道管理
- 吸痰记录：时间、方式（闭式/开放）、效果、SpO₂变化（可选）
- 湿化/雾化记录
- VAP bundle 执行项（与院感模块联动）

#### 4.2.8 皮肤与口腔护理记录
- 皮肤完整性检查：重点部位勾选与备注
- 口腔护理执行记录：频次、异常发现
- 护理提醒：忙时易漏项的自动提醒

#### 4.2.9 护理路径管理
- 按病种/方案生成护理任务包（如脓毒症、ARDS、术后镇静等）
- 路径版本管理：模板更新不影响历史记录
- 路径执行率统计

#### 4.2.10 护理文书自动生成
- 自动生成交接摘要
- 自动生成班次护理小结（建议稿）：基于任务完成、关键异常、评分变化
- 生成内容可编辑，最终提交留痕

#### 4.2.11 护理缺失提醒
- 缺失类型：
  - 漏巡：到期未完成
  - 关键记录缺失：体征/出入量/评分缺失
  - 管路未评估：留置必要性未做
- 缺失提醒分级：普通提醒/强提醒/阻断提交（可配置）
- 缺失看板：护士个人、病区汇总

### 4.3 关键数据对象
- `handover`：交接单（模板+实例）
- `task_template` / `task`：任务模板与任务实例（巡视、翻身、吸痰等）
- `nursing_record`：护理记录（结构化+文本）
- `score_record`：评分记录（APACHE/SOFA/GCS）
- `line`：管路/导管主档 + `line_maintenance_record`（可选）
- `pressure_injury_assessment` / `pressure_injury_event`（可选）
- `airway_care_record`、`oral_care_record`（可选，亦可用表单引擎承载）
- `missing_alert`：缺失提醒事件（可选但建议）

### 4.4 关键接口建议
- 交接
  - `GET /api/handover/templates` 获取交接模板（可配置）
  - `POST /api/handover` 创建交接单（草稿）
  - `POST /api/handover/{id}/confirm` 双方确认
  - `GET /api/handover?icu_stay_id=&from=&to=` 交接历史
- 任务/巡视
  - `GET /api/tasks/templates?ward_id=` 任务模板（按病区）
  - `POST /api/tasks/generate` 按模板生成当班任务（按床/按护士）
  - `GET /api/tasks?assignee_id=&status=&from=&to=` 任务列表
  - `POST /api/tasks/{id}/done` 完成任务（附记录）
- 护理记录
  - `POST /api/nursing-records` 新增护理记录
  - `GET /api/nursing-records?icu_stay_id=&from=&to=` 列表
  - `PUT /api/nursing-records/{id}` 修改（需理由，强审计）
- 评分
  - `POST /api/scores/calc` 触发计算（或定时任务）
  - `GET /api/scores?icu_stay_id=&type=&from=&to=` 查询评分
  - `POST /api/scores/manual` 手工补录
- 管路
  - `POST /api/lines` 新增管路
  - `POST /api/lines/{id}/daily-check` 留置必要性评估
  - `POST /api/lines/{id}/maintenance` 维护记录（可选）
  - `POST /api/lines/{id}/remove` 拔除
  - `GET /api/lines?icu_stay_id=` 列表
- 压疮/翻身
  - `POST /api/turning-records` 翻身执行记录（或任务done里携带）
  - `POST /api/pressure-injury/assessments` 压疮评估
  - `POST /api/pressure-injury/events` 压疮事件
- 呼吸道/口腔/皮肤（可先用表单引擎统一承载）
  - `POST /api/forms/{code}/records`（例如 `airway_care`/`oral_care`）
- 缺失提醒
  - `GET /api/missing-alerts?ward_id=&type=&status=` 缺失列表
  - `POST /api/missing-alerts/{id}/ack` 已知晓/已处理

### 4.5 权限与审计要点
- 交接确认：必须审计（谁确认、何时确认、交接差异）
- 护理记录修改：高风险，必须字段级留痕 + 修改原因
- 评分计算：需记录计算依据的时间窗版本（避免争议）
- 涉及照片/附件：单独权限，访问产生审计事件
- 缺失阻断策略：通过配置中心控制，避免“一刀切影响临床”

## 五、医嘱与用药闭环模块

### 5.1 目标
实现“结构化医嘱—审核—床旁核对—执行—反馈—追溯”闭环，重点保障 ICU 高频、高风险用药（血管活性药、镇静镇痛等）执行安全，并与输注泵联动，减少漏执行与剂量差错。

### 5.2 功能清单

#### 5.2.1 结构化医嘱录入
- 医嘱类型：药品、检验、处置、营养（可分期）
- 字段结构化：剂量、途径、频次、开始/停止、注意事项
- 与HIS对接（可选）：拉取/推送医嘱，维护映射字典（药品/频次）

#### 5.2.2 医嘱审核流程
- 审核角色：医生二次确认、药师审核（按院内流程配置）
- 审核状态流转：草稿→待审→通过/退回→执行中→停止
- 审核意见留痕与追溯

#### 5.2.3 条码核对机制
- 核对对象：人（腕带）-药（药袋/安瓿）-医嘱（系统）-执行人
- 核对结果：成功/失败原因（腕带缺失、药码不匹配等）
- 离线兜底（可选）：网络异常下的临时执行与补录审计

#### 5.2.4 输注泵联动
- 泵参数关联医嘱：速率/剂量与医嘱一致性校验
- 泵启动/停止与执行记录联动（可选）
- 泵报警联动告警模块（可选）

#### 5.2.5 高警示药物提醒
- 高警示药库（字典维护）：去甲肾上腺素、丙泊酚等
- 提醒策略：双人复核、剂量上限、变更强提醒（策略可配置）
- 记录复核人（可选）

#### 5.2.6 过敏与禁忌校验
- 过敏史维护（来自HIS或手录）
- 过敏触发：强阻断/强提醒（策略可配置）
- 禁忌校验：基础版可只做“规则+字典”校验，后续再扩展CDSS

#### 5.2.7 漏执行自动提醒
- 漏执行定义：超过计划执行时间窗未执行
- 提醒对象：责任护士/当班护士/护士长（可配置）
- 闭环：提醒→补执行/取消原因→统计

#### 5.2.8 医嘱执行日志追踪
- 执行记录：执行人、时间、核对方式、执行结果、备注
- 变更追踪：医嘱变更前后对比（剂量/频次/停止）
- 导出：按患者/时间段导出执行清单（导出权限严格控制）

### 5.3 关键数据对象
- `order`：医嘱主数据（结构化字段 + 状态）
- `order_audit`：审核记录（谁审、意见、时间）
- `order_execution`：执行记录（含条码核对结果）
- `barcode_map`：条码与物品/药品映射（可选）
- `high_alert_drug`：高警示药字典（可与 dict 合并）
- `allergy_record`：过敏史（可与 patient 扩展或独立表）
- `pump_link`：医嘱-泵绑定（可选）
- `order_overdue_alert`：漏执行提醒事件（可选）

### 5.4 关键接口建议
- 医嘱
  - `GET /api/orders?icu_stay_id=&status=&type=` 医嘱列表
  - `POST /api/orders` 新建医嘱（系统内开立时）
  - `PUT /api/orders/{id}` 修改医嘱（需权限+审计）
  - `POST /api/orders/{id}/stop` 停止医嘱
  - `POST /api/orders/import` HIS同步（可选）
- 审核
  - `POST /api/orders/{id}/submit-audit` 提交审核
  - `POST /api/orders/{id}/audit/approve` 审核通过
  - `POST /api/orders/{id}/audit/reject` 审核退回
  - `GET /api/orders/{id}/audit-records` 审核历史
- 执行与核对
  - `POST /api/orders/{id}/barcode-check` 条码核对
  - `POST /api/orders/{id}/execute` 执行医嘱（记录执行日志）
  - `GET /api/orders/{id}/executions` 执行历史
- 泵联动（可选）
  - `POST /api/orders/{id}/bind-pump` 绑定泵
  - `POST /api/orders/{id}/unbind-pump` 解绑泵
  - `GET /api/orders/{id}/pump` 查看联动状态
- 高警示/过敏禁忌
  - `GET /api/drugs/high-alert` 高警示药列表（字典）
  - `POST /api/patients/{id}/allergies` 维护过敏史
  - `GET /api/orders/{id}/safety-check` 返回过敏/禁忌/剂量上限检查结果
- 漏执行提醒
  - `GET /api/alerts/order-overdue?ward_id=&status=` 漏执行列表
  - `POST /api/alerts/order-overdue/{id}/ack` 知晓/处理

### 5.5 权限与审计要点
- 医嘱创建/修改/停止：必须审计（前后对比），event_type：`order_change`
- 审核通过/退回：必须审计，event_type：`order_audit`
- 条码核对失败：必须记录（用于质量改进），可写审计事件 `barcode_mismatch`
- 高警示药执行：建议强制二次确认/双人复核（可配置），并审计
- 泵联动参数不一致：强提醒并记录事件 `pump_mismatch`
- 漏执行：必须形成事件并可统计闭环率

## 六、实时监护与告警管理模块

### 6.1 目标
统一管理 ICU 的“设备报警 + 规则报警 +（可选）AI报警”，实现分级、聚合、确认/抑制留痕、响应时间统计与疲劳治理，形成可闭环处置与持续优化的告警治理体系，降低漏报与报警疲劳导致的风险。

### 6.2 功能清单

#### 6.2.1 实时监护大屏
- 大屏维度：院区/病区/护理单元
- 展示内容（可配置）：
  - 床位一览：床位状态、患者摘要、关键体征/趋势、风险标签
  - 告警态势：未处理高危告警数、近1小时告警曲线
  - 关键风险提示：评分变化、液体平衡异常（可选）
- 自动刷新：10s/30s（可配置），支持大屏轮播（可选）
- 大屏权限：只读；禁止导出；敏感信息脱敏显示

#### 6.2.2 告警分级管理
- 告警级别：高/中/低（可扩展：危急）
- 分级策略可配置：按来源/告警类型/患者个体化阈值
- 分发策略：
  - 高危：强提醒 + 多端推送 + 超时升级
  - 中危：常规提醒
  - 低危：聚合展示为主

#### 6.2.3 告警聚合机制
- 合并规则：同一患者、同一告警类型、冷却窗口内合并
- 去重：同一来源重复上报按 fingerprint 去重
- 聚合组展示：组内次数、起止时间、最新状态
- 保留原始明细：聚合不丢失 raw 事件

#### 6.2.4 告警确认与抑制
- 确认（ACK）：确认人、确认时间、备注（可选）
- 抑制（Silence）：抑制时长/截止时间、原因必填（可配置）
- 抑制上限：高危告警默认限制最大抑制时长（可配置）
- 到期自动恢复：抑制到期自动恢复提醒/状态回滚

#### 6.2.5 告警响应时间统计
- 响应时间口径（可配置）：
  - 响应时间 = 触发时间 → 首次确认时间
  - 关闭时间 = 触发时间 → 关闭时间
- 统计维度：病区/班次/告警类型/人员
- 输出：均值/中位数/90分位、超时占比

#### 6.2.6 报警疲劳治理
- 策略库（可配置）：
  - 误报过滤：电极脱落、体位短暂异常等
  - 冷却窗口：X分钟内不重复强提醒
  - 组合告警：多个低危聚合为中危提示
  - 个体化阈值：按患者模板调整（需留痕/审批可选）
- 有效性分析：有效报警占比、误报原因TopN

#### 6.2.7 告警处置闭环
- SOP配置（可选）：按告警类型配置处置建议/检查清单
- 处置记录：处置动作、结果、是否误报、是否升级通知
- 升级规则：超过阈值自动升级通知护士长/医生（可配置）
- 处置结果沉淀（可选）：
  - 自动写入护理记录摘要/交接摘要

#### 6.2.8 告警优化分析
- 告警量/床日、类型TopN、高危占比
- 响应超时TopN、抑制次数TopN
- 治理建议（可选）：阈值调整建议、设备维护建议、班次负荷建议

### 6.3 关键数据对象
- `alarm_raw`：原始告警事件（来源设备/规则/AI）
- `alarm`：治理后的告警主对象（分级、聚合、状态）
- `alarm_group`：聚合组（可选）
- `alarm_action`：动作流水（ack/silence/close/escalate）
- `alarm_rule`：规则告警配置（阈值/趋势/冷却/分发）
- `alarm_fatigue_policy`：疲劳治理策略（可与配置中心合并）
- `alarm_escalation`：升级记录（可选）
- `alarm_stat`：统计结果（可实时算或预聚合）

### 6.4 关键接口建议
- 大屏
  - `GET /api/monitoring/board?ward_id=` 实时大屏（床位+告警摘要）
  - `GET /api/monitoring/bed/{bed_id}` 单床实时卡片
- 告警
  - `GET /api/alarms?ward_id=&level=&status=&from=&to=&keyword=` 列表
  - `GET /api/alarms/{id}` 详情（含raw/聚合信息）
  - `GET /api/alarms/{id}/actions` 动作历史
  - `POST /api/alarms/{id}/ack` 确认
  - `POST /api/alarms/{id}/silence` 抑制（入参：silenced_until 或 duration + reason）
  - `POST /api/alarms/{id}/close` 关闭（入参：result_code、result_note、is_false_alarm）
- 规则与治理
  - `GET /api/alarm/rules?ward_id=` 规则列表
  - `POST /api/alarm/rules` 新建规则
  - `PUT /api/alarm/rules/{id}` 修改规则
  - `POST /api/alarm/rules/{id}/enable` 启用/停用
  - `GET /api/alarm/fatigue/policies?ward_id=` 疲劳策略
  - `PUT /api/alarm/fatigue/policies` 更新策略
- 统计与分析
  - `GET /api/alarm/stats/overview?ward_id=&from=&to=` 总览
  - `GET /api/alarm/stats/response-time?ward_id=&from=&to=&group_by=` 响应时间
  - `GET /api/alarm/stats/top?ward_id=&from=&to=&metric=` TopN

### 6.5 权限与审计要点
- 告警确认/抑制/关闭：高风险，必须审计（原因、时长、前后状态）
- 规则阈值变更：全局风险，必须审计（前后对比），建议仅管理员可改
- 大屏只读：禁止导出，敏感字段脱敏
- 升级通知触发：记录审计事件（event_type：alarm_escalation）

### 6.6 权限点建议（就近）
- 菜单：
  - `menu.icu.monitoring.board`（监护大屏）
  - `menu.icu.alarm`（告警中心）
- API：
  - `api.icu.monitoring.board`
  - `api.icu.alarms.list/detail/actions/ack/silence/close`
  - `api.icu.alarm.rules.list/create/update/enable`
  - `api.icu.alarm.fatigue.policies.get/update`
  - `api.icu.alarm.stats.overview/response_time/top`
- 按钮：
  - `btn.icu.alarm.ack` / `btn.icu.alarm.silence` / `btn.icu.alarm.close`
  - `btn.icu.alarm.rule.edit`

## 七、感染控制与院感管理模块

### 7.1 目标
对齐 ICU 目标性监测要求，实现 VAP/CLABSI/CAUTI 等器械相关感染的“每日必要性评估—Bundle执行记录—事件监测—趋势分析”闭环，并支持隔离管理与探视管理，降低院感风险与纠纷风险。

### 7.2 功能清单

#### 7.2.1 导管相关感染监测（总框架）
- 覆盖：中心静脉导管（CVC/PICC）、导尿管、气道（ETT/气切）等
- 关键口径：
  - 器械日（device-days）：按留置天数计算
  - 发生率：每千器械日（口径可配置）
- 数据联动：来自“管路管理模块”置入/拔除 + 每日评估 + 维护记录

#### 7.2.2 VAP监测
- VAP bundle 执行项配置（可选按院内要求）
- 执行记录：按日/按班次
- VAP事件登记：疑似/确诊、时间、证据摘要、关联气道留置

#### 7.2.3 CLABSI监测
- CLABSI bundle：无菌、敷料更换、必要性评估等
- 中心静脉导管器械日统计
- CLABSI事件登记与追溯

#### 7.2.4 CAUTI监测
- CAUTI bundle：留置评估、维护措施等
- 导尿器械日统计
- CAUTI事件登记与追溯

#### 7.2.5 留置必要性每日评估
- 每条管路每日评估“是否继续留置”
- 提醒策略可配置：提醒/强提醒/阻断（与交接/当班小结联动可选）
- 合规率统计：漏评估率、按班次/人员/床位分析

#### 7.2.6 手卫生依从性记录
- 基础版：抽查记录（人员、时点、是否合规、备注）
- 可选：对接手卫生设备自动记录
- 统计：依从率趋势、问题点位分析

#### 7.2.7 隔离管理
- 隔离类型：接触/飞沫/空气/保护性（字典）
- 隔离开始/解除：记录原因、时间、执行人
- 联动：床位卡片标识、探视防护要求提示、终末清洁记录（可选）

#### 7.2.8 探视管理
- 探视规则配置：时段、人数、特殊审批（可选）
- 探视预约（可选）：预约登记、审批
- 探视记录：实际探视、人员、宣教确认、风险告知电子确认
- 与隔离联动：隔离患者探视限制与防护提示

#### 7.2.9 感染趋势分析
- 趋势看板：
  - VAP/CLABSI/CAUTI发生率趋势
  - 器械日趋势、bundle执行率趋势
  - 隔离床位占用与周转
- 异常预警（可选）：短期升高、床位/班次聚集

### 7.3 关键数据对象
- `line`：管路/导管主档（来自护理工作台）
- `line_daily_necessity`：每日必要性评估记录（可复用管路daily-check流水）
- `bundle_template`：bundle模板（按VAP/CLABSI/CAUTI）
- `bundle_record`：bundle执行记录（按日/班次/患者）
- `infection_event`：感染事件（疑似/确诊/排除）
- `hand_hygiene_record`：手卫生抽查/设备记录
- `isolation_record`：隔离记录
- `visit_rule` / `visit_appointment` / `visit_record`：探视规则/预约/记录
- `infection_stat`：院感统计与趋势（可预聚合）

### 7.4 关键接口建议
- Bundle与必要性评估
  - `GET /api/infection/bundles/templates?ward_id=` 模板
  - `POST /api/infection/bundles/records` 执行记录（icu_stay_id、type、date/shift、items）
  - `GET /api/infection/bundles/records?icu_stay_id=&type=&from=&to=` 查询
  - `POST /api/lines/{id}/necessity` 留置必要性评估（可复用管路接口）
- 感染事件
  - `POST /api/infection/events` 新增（疑似/确诊/排除）
  - `PUT /api/infection/events/{id}` 更新（证据/状态）
  - `POST /api/infection/events/{id}/close` 关闭（结论/处置）
  - `GET /api/infection/events?ward_id=&type=&status=&from=&to=` 列表
- 手卫生
  - `POST /api/hand-hygiene/records` 抽查记录
  - `GET /api/hand-hygiene/stats?ward_id=&from=&to=` 依从率统计
- 隔离
  - `POST /api/isolation/start` 开始隔离（icu_stay_id、type、reason）
  - `POST /api/isolation/stop` 解除隔离（icu_stay_id、reason）
  - `GET /api/isolation?ward_id=&status=` 隔离列表
- 探视
  - `GET /api/visits/rules?ward_id=` 规则
  - `PUT /api/visits/rules` 更新规则（管理员）
  - `POST /api/visits/appointments` 预约（可选）
  - `POST /api/visits/appointments/{id}/approve` 审批（可选）
  - `POST /api/visits/records` 实际探视登记
  - `GET /api/visits/records?icu_stay_id=&from=&to=` 探视记录
- 趋势分析
  - `GET /api/infection/stats/overview?ward_id=&from=&to=` 总览
  - `GET /api/infection/stats/trend?ward_id=&metric=&from=&to=` 趋势

### 7.5 权限与审计要点
- 感染事件新增/确诊/关闭：必须审计（院感与纠纷高敏）
- 隔离开始/解除、探视审批：必须审计
- 探视数据：隐私访问需审计（可标记 sensitive_read）
- 模板/规则变更：仅管理员可改，审计前后差异与版本
- 指标展示：避免公开点名排名（可做管理员可见）

  - `menu.icu.infection`（院感管理）

  - `api.icu.infection.bundles.templates/records_create/records_list`
  - `api.icu.infection.events.create/update/close/list`
  - `api.icu.hand_hygiene.records_create/stats`

  - `api.icu.visits.rules_get/rules_update/appointments_create/appointments_approve/records_create/records_list`

## 八、患者安全与质量管理模块

### 8.1 目标
对齐国家护理质控与院内质量安全要求，实现：风险评估（跌倒/压疮/拔管）→ 事件上报（非惩罚性）→ 分级处置 → RCA根因分析 → 整改追踪 → 指标看板闭环，形成可量化改进与可追溯证据链。

### 8.2 功能清单

#### 8.2.1 跌倒风险评估
- 评估表（可配置）：意识、活动能力、药物、既往史等
- 触发：入科、状态变化、每班（可配置）
- 风险等级：低/中/高
- 联动：高风险标识显示在床位卡片、交接摘要

#### 8.2.2 压疮风险评估
- 工具：Braden等（可配置）
- 频次：入科、每日、变化（可配置）
- 联动（可选）：自动生成翻身/皮肤检查任务包

#### 8.2.3 非计划拔管监测
- 监测对象：气管插管/气切、CVC/PICC、胃管、尿管等（字典）
- 事件字段：发生时间、管路类型、原因初判、后果、是否再置管
- 统计：发生率（每千器械日/每千床日，口径可配置）

#### 8.2.4 不良事件上报系统
- 上报模式：匿名/非匿名（可配置），页面提示非惩罚文化
- 上报字段：类型、严重度、时间地点、经过、初因、附件
- 流程：上报→复核/分级→RCA→整改→验证→关闭

#### 8.2.5 事件分级机制
- 分级维度：伤害程度、潜在风险、可逆性、影响范围
- 分级模板可配置：不同医院口径可调整
- 高等级事件：自动通知管理层并设置强制时限

#### 8.2.6 RCA根因分析模板
- 模板可配置：人因/流程/设备/环境/沟通/培训/系统等
- 支持：5 Why、鱼骨图字段（可选）
- 输出：根因、措施、责任人、期限、验证方式

#### 8.2.7 整改追踪
- 整改项任务化：责任人、截止时间、状态、证据附件
- 逾期提醒与升级提醒
- 关闭条件：验证通过后方可关闭事件

#### 8.2.8 国家护理质控指标对齐
- 指标字典化（可配置）：跌倒、压疮、非计划拔管、院感等
- 指标自动取数：
  - 分子：事件表
  - 分母：床日/器械日
- 口径版本：口径变更版本化并审计（历史一致性）

#### 8.2.9 质量驾驶舱
- 展示：趋势、Top类型、闭环率、逾期率、班次分布
- 钻取：指标→事件列表→事件详情→RCA/整改
- 权限：管理层可见；一线默认只看与自己/本病区相关（可配置）

### 8.3 关键数据对象
- `risk_assessment`：风险评估（跌倒/压疮等，建议用表单引擎承载）
- `quality_event`：不良事件（类型、分级、状态、关联患者/床位）
- `quality_event_flow`：事件流转记录（可选）
- `rca_case`：RCA记录（模板+内容）
- `corrective_action`：整改项（责任人/期限/状态/证据）
- `quality_metric_definition`：指标定义（口径、分子分母规则）
- `quality_metric_stat`：指标统计（可预聚合）
- `quality_dashboard_config`：驾驶舱配置（可选）

### 8.4 关键接口建议
- 风险评估（建议用表单引擎统一）
  - `GET /api/risk/templates?type=fall/pressure` 模板
  - `POST /api/risk/assessments` 提交评估（或 `POST /api/forms/{code}/records`）
  - `GET /api/risk/assessments?icu_stay_id=&type=&from=&to=` 查询
- 不良事件
  - `POST /api/quality/events` 上报
  - `GET /api/quality/events?ward_id=&type=&level=&status=&from=&to=` 列表
  - `GET /api/quality/events/{id}` 详情（含RCA/整改）
  - `POST /api/quality/events/{id}/classify` 分级/复核
  - `POST /api/quality/events/{id}/close` 关闭（需验证整改）
- RCA与整改
  - `GET /api/quality/rca/templates` RCA模板
  - `POST /api/quality/events/{id}/rca` 保存RCA
  - `POST /api/quality/events/{id}/actions` 新增整改项
  - `PUT /api/quality/actions/{action_id}` 更新整改项（状态/证据）
  - `GET /api/quality/actions?assignee_id=&status=` 整改待办
- 指标与驾驶舱
  - `GET /api/quality/metrics/definitions` 指标定义
  - `PUT /api/quality/metrics/definitions/{id}` 更新口径（管理员）
  - `GET /api/quality/metrics/stats?ward_id=&from=&to=&metric=` 指标趋势
  - `GET /api/quality/dashboard/overview?ward_id=&from=&to=` 驾驶舱总览

### 8.5 权限与审计要点
- 事件上报：普通护士可上报；但分级/关闭/RCA需更高权限

## 十一、AI增强模块

### 11.1 目标
在“数据底座 + 闭环流程”基础上提供可控、可解释、可审计的AI能力：风险预测、报警过滤、文书辅助生成。AI输出以“建议稿/建议值”为主，必须可回滚、可停用、可记录临床反馈。

#### 11.2.1 脓毒症预测（示例）
- 输入：体征、检验（可选）、用药、评分、趋势特征
- 输出：风险分数/等级、触发原因摘要、建议动作（如复查乳酸、通知医生）

#### 11.2.2 呼吸衰竭趋势预测（示例）
- 输入：呼吸机参数、SpO₂、RR、血气（可选）
- 输出：未来X小时风险趋势、关键因素

#### 11.2.3 再插管风险预测（示例）
- 输入：拔管前参数、意识评分、呼吸参数趋势
- 输出：风险等级与建议（如延后拔管/加强监测）

#### 11.2.4 ICU再入预测（示例）
- 输入：出科前关键指标、评分变化、护理任务完成情况（可选）
- 输出：风险等级与随访建议

#### 11.2.5 智能报警过滤（报警疲劳治理增强）
- 将“低价值报警”降级或聚合提示（需非常谨慎）
- 必须保留原始报警，且可一键关闭该策略

#### 11.2.6 个体化阈值调整建议
- 输出“建议阈值”，由临床确认后生效（可走审批）
- 阈值生效需记录版本与时间窗

#### 11.2.7 文书自动生成
- 交接摘要建议稿
- 当班护理小结建议稿
- 要求：可编辑、最终提交留痕；禁止自动直写为“最终文书”

#### 11.2.8 风险因素可解释展示
- 展示Top因素贡献（简化解释，不一定要SHAP）
- 说明数据时间窗与来源（便于临床信任）

#### 11.2.9 模型版本管理
- 模型启用/停用
- 灰度发布：按病区/按床位/按比例（可选）
- 回滚机制：一键回到上个版本
- 漂移监控（可选）：数据分布变化、性能提示

### 11.3 关键数据对象
- `ai_model`：模型定义（code、版本、状态、配置）
- `ai_deployment`：部署策略（范围、灰度比例、启停时间，可选）
- `ai_prediction`：预测记录（时间、分数、等级、解释、建议）
- `ai_feedback`：临床反馈（采纳/忽略/反驳原因）

### 11.4 关键接口建议

### 11.5 权限与审计要点

- 以“趋势与结构”为主，避免直接用于绩效争议

#### 12.2.9 多维数据钻取

# 状态机定义（文档末尾统一）

> 说明：状态机用于前后端一致实现：按钮可用性、流程校验、统计口径。  
> 约定：任何状态变更必须写 `op_log`（前后对比）并按模块写 `audit_event`。

## S1. 告警状态机（alarm.status）

### 状态集合
- `new`：新触发未处理
- `acked`：已确认
- `silenced`：已抑制（到期可回到 new 或保持 acked，按策略）
- `closed`：已关闭

### 事件与迁移
- 触发告警：`(none) -> new`
- 确认：`new -> acked`
- 抑制：
  - `new -> silenced`
  - `acked -> silenced`
- 抑制到期：
  - `silenced -> new`（默认，代表仍未确认但恢复提醒）
  - 或 `silenced -> acked`（可选策略：若抑制前已确认）
- 关闭：
  - `new -> closed`（允许但建议要求原因，或禁止可配置）
  - `acked -> closed`
  - `silenced -> closed`

### 约束建议
- 高危告警抑制时长上限（配置）
- `closed` 为终态；如需重开：新建一条告警（保留追溯）

---

## S2. 感染事件状态机（infection_event.status）

### 状态集合
- `suspected`：疑似
- `confirmed`：确诊
- `excluded`：排除
- `closed`：结案（可选，若需要把 confirmed/excluded 也进一步结案）

### 事件与迁移
- 新增：`(none) -> suspected`
- 确诊：`suspected -> confirmed`
- 排除：`suspected -> excluded`
- 结案（可选）：
  - `confirmed -> closed`
  - `excluded -> closed`

### 约束建议
- `confirmed/excluded/closed` 变更必须填写证据摘要与操作人
- 状态回退需更高权限并强审计（一般不建议回退）

---

## S3. 质量事件状态机（quality_event.status）

### 状态集合
- `reported`：已上报
- `in_review`：复核/分级中
- `rca_required`：需要RCA（通常中高等级）
- `action_in_progress`：整改进行中
- `verified`：已验证
- `closed`：已关闭

### 事件与迁移
- 上报：`(none) -> reported`
- 复核/分级：`reported -> in_review`
- 判断需要RCA：`in_review -> rca_required`
- RCA提交完成：`rca_required -> action_in_progress`
- 整改完成并提交验证：`action_in_progress -> verified`
- 关闭：`verified -> closed`

### 约束建议
- `closed` 前必须满足：
  - 必要的 RCA 已提交（若等级要求）
  - 所有整改项 `done` 且有证据
  - 验证人确认
- 允许低等级事件走简化路径：
  - `in_review -> verified -> closed`（无需RCA，可配置）

---

## S4. 整改项状态机（corrective_action.status）

### 状态集合
- `todo`：待执行
- `doing`：进行中
- `done`：已完成（待验证）
- `verified`：已验证
- `cancelled`：取消（需原因）

### 事件与迁移
- 创建：`(none) -> todo`
- 开始执行：`todo -> doing`
- 提交完成：`doing -> done`
- 验证通过：`done -> verified`
- 取消：
  - `todo -> cancelled`
  - `doing -> cancelled`（需更高权限）

### 约束建议
- `done -> verified` 需验证人角色（非执行人，避免自证）
- `cancelled` 必须填写取消原因

---

## S5. 探视预约状态机（visit_appointment.status）

> 若未做“预约”，只做“探视记录”，此状态机可不启用。

### 状态集合
- `submitted`：已提交
- `approved`：已审批通过
- `rejected`：已拒绝
- `cancelled`：申请人取消
- `checked_in`：已到访登记（可选）
- `completed`：已完成（探视结束）

### 事件与迁移
- 提交预约：`(none) -> submitted`
- 审批通过：`submitted -> approved`
- 拒绝：`submitted -> rejected`
- 取消：
  - `submitted -> cancelled`
  - `approved -> cancelled`（可配置是否允许）
- 到访登记（可选）：`approved -> checked_in`
- 完成：`checked_in -> completed`（或 `approved -> completed` 若不做check-in）

### 约束建议
- `approved/rejected` 必须记录审批人、时间、意见
- 隔离患者预约：必须校验隔离类型对应规则（可配置阻断或提示）
- 预约通过后若规则变更：不影响已批准预约，但需提示（可选）
